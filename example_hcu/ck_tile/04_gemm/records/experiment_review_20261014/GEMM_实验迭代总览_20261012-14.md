## 4. 关键优化点：具体修改方法、代码与验证

本节展开11个有效优化点，再说明两个有代表性的负结果。每个优化点都给出修改前后、实现位置和效果；可直接配合源码阅读。`T`代表TFLOPS，数据来自已有实验。

下面代码中的 `MMAC`、`load_async`、`consume` 等为**算法伪代码**，用于压缩索引、展开和同步逻辑，不能直接复制编译。特别是producer与consumer代码在不同wave上并发执行，画在相邻位置不表示同一线程顺序调用。真实边界条件、寄存器约束、屏障与终末等待以链接源码及对应冻结版本为准。

当前源码行号在2026-10-14核对；历史源码应通过[实测库源码索引](GEMM_源码与构建索引.md)中的SHA和冻结目录查找。以下内部 **A=权重W，B=激活X**，适用于AC交换操作数之后的主线。

### 4.1 扩大输出tile、调整LDS布局，并解决寄存器spill（A–O）

**原来的问题。** 起点为128×128输出tile、BK32。每CTA装入两份操作数后只产生较小输出tile，操作数的计算复用有限。扩大tile能提高复用，但也需要更多累加器，早期大tile/768-thread候选遭遇编译器寄存器分配限制和spill，不能只改tile尺寸。

**具体修改。** 分三步验证，而非一次把所有参数改大：

1. 在 `build.py` 的候选配置中比较128×128、128×256、256×128、256×256及wave划分。由 `gemm.cpp` 的 `TileGemmShape` 实例化对应CK模板。
2. 在私有 `padded_policy.hpp` 中改变LDS物理行跨度，逻辑坐标不变：

   ```cpp
   // 旧的连续行布局：物理索引概念式
   lds_index = row * BK + col;

   // padding候选
   lds_index = row * (BK + PAD) + col;  // 比较PAD=8/16
   // A/B descriptor、LDS容量计算同时更新，不能只改写入地址。
   ```

3. 对需要该资源的候选编译加入本机DTK选项：

   ```bash
   -mllvm --enable-num-vgprs-768=true
   ```

   这使编译器能为768-thread配置使用足够VGPR；必须再检查实际ELF的VGPR、scratch和spill。它不增加硬件寄存器总量，也不保证所有候选更快。

**为什么可能快。** 忽略缓存和输出，仅看一个K片段，输入量约为 `2*BK*(BM+BN)` 字节，数学量为 `2*BM*BN*BK` FLOPs。tile变大时，每次搬入的元素服务更多乘加；padding则改变LDS物理访问分布。若累加器溢出到scratch，额外流量和依赖会抵消复用收益。

**实际结果。** FC2约67.88T起步，宽tile约105.02T，padding16阶段约138.21T，wave/CTA组合约149.56T，大tile配足够寄存器后约187.84T。它们是不同阶段的里程碑，不能把差值都归给编译选项。N轮分工原型84VGPR并大量spill时只有约4.6T，放开限制后原型约132T；O轮通用大tile202VGPR、无spill才达到约188T。

**counter证据。** 早期DTK工具报告base→wide_pad16的LDS指令77.97M→72.40M、bank-conflict445.56M→133.67M。相关条目部分emulated，只能与实现/计时共同解释，不能当作实际stall周期。此处没有每个tile配置的独立xprof完整对照。

**源码与原始结果。** [gemm.cpp:79](<../gemm.cpp:79>)、[padded_policy.hpp:5](<../padded_policy.hpp:5>)、[build.py](<../build.py>)；阶段 `stage_b_tiles`、`stage_e_lds_padding`、`stage_o_register_pool`。后期rolephase采用的是经过硬件探针验证的wrap布局，不是一直沿用早期padding16。

### 4.2 恢复连续K方向的vec8读取，同时保留尾行保护（AF）

**原来的问题。** AC/AD把内部方向改成W@X.T后，激活B是ColumnMajor视图，实际连续方向仍是K。共享Problem的启发式遇到 `kPadN` 就把 `VectorSizeB` 设为1，导致合法的连续K读取被标量化。AD约50–54T的退化来自这条路径，而当时另一个旧通用大tile仍约188T。

**具体修改。** 仅对实验的私有Problem覆盖向量宽度，不关掉N尾部padding：

```cpp
// 修改前：直接使用BaseProblem，kPadN影响VectorSizeB推导
using Problem = BaseProblem;

// 修改后：此实验的B地址满足连续K、16-byte base对齐
struct Problem : BaseProblem {
    static constexpr ck_tile::index_t VectorSizeB = 8;
};
```

BF16每个元素2字节，vec8一次读取16字节。接口同时检查输入16-byte对齐、K%8等约束，编译期核对BK；tensor view的尾行保护继续生效。不能把该覆盖无条件搬到任意stride或非对齐输入。

**实际变化。** ISA静态 `buffer_load_ushort` 32→0、`buffer_load_dwordx4` 4→8，说明读取确实向量化。真实M18880四shape分别206.14/212.61/203.08/212.49T，相对同期旧通用大tile约187.60/183.90/164.90/183.91T更快；相对约50T的AD退化路径，则是修复了向量化损失。这两种对照不能混成一个百分比。

**xprof证据。** 没有AF单独配对的counter采集；本项依据源码推导、ISA及无profiler计时判断，不把后期AU/BP的counter当作AF结果。

**源码与验证。** [gemm.cpp:88](<../gemm.cpp:88>)为覆盖，输入契约见[gemm.cpp:151](<../gemm.cpp:151>)。宏 `H3_CONTIGUOUS_B_VECTOR=1`；阶段 `stage_af_contiguous_vector_restore` / `stage_af_native_m18880`，四shape、finite和M尾部输出guard通过。

### 4.3 权重走LDS、激活走VGPR；用K32双bank控制预取寿命（AI/AK）

**原来的问题。** 较早K64原型一次管理较大的B片段，寄存器存活范围和搬运安排不理想。即使双缓冲，过早等待所有VMEM或把future复制到current，也可能降低重叠效果。

**具体修改。** 新 `rolephase.cpp` 按角色分工：4个producer wave把权重A通过HCU direct-to-LDS搬进两个K64槽；8个compute wave从LDS读A、直接把激活B加载到自己的VGPR。一个K64数学tile拆成两个K32 phase，B用两个固定bank轮换。

```cpp
// 较早的概念形式：current/future及推进
future = load_B(next_phase);
wait_until_ready();
MMAC(A_current, current);
current = future;

// AK的banked asm路径，示意一个非终末phase
bank[next_bank] = load_B_async(next_phase);  // NT=2条16-byte load
wait_vmcnt(2);  // 允许更新的2条future在途；更老current必须完成
MMAC(A_current, bank[current_bank]);
// 下一phase交换bank角色；无需显式current=future
```

`vmcnt(2)`的依据是此compute wave的真实加载序列：current比future老，每phase发NT=2条B读取。producer wave自己的VMEM计数不与该wave混在一起。startup必须先完成初始bank；终末没有有效future时必须完整等待。NT或加载顺序改变后，阈值必须重新推导。

**为什么可能快。** B的在途数据和寄存器生命周期缩到K32片段，旧数据消费与下一片段搬运可以重叠；固定bank给编译器更明确的目的寄存器生命周期。1×8 compute划分还使B片段在同一wave内复用更多权重数学片段。

**实际结果。** AI约225.87/228.75/212.51/228.90T；AK双bank+asm显式等待为239.08/239.81/222.53/239.82T。普通LLVM双bank或附加priority没有相同收益，不能把结果全归于“双bank”三个字。

**counter证据。** AI旧phase→AK的DTK VM完成等待均值364.24M→115.24M，但旧phase范围197.56M–697.04M很宽；barrier717.46M→637.83M、LDS issue114.05M→155.86M。只能说明等待结构改变，不能写“内存延迟稳定下降69%”。

**源码与验证。** B加载选择在[rolephase.cpp:380](<../rolephase.cpp:380>)，bank/startup在[rolephase.cpp:691](<../rolephase.cpp:691>)，current/future等待在[rolephase.cpp:821](<../rolephase.cpp:821>)；宏 `H3_PHASE_BANK=1`、`H3_PHASE_ASM_B=1`。阶段 `stage_ai_phase_register_prefetch`、`stage_ak_banked_wait_schedule`；AK另有72组/216次广审计。

### 4.4 把未来B加载插入DS读取中间，并去掉热循环的终末条件（AP–AT）

**原来的问题。** 即使有双bank，把整段DS读取和VMEM发射排成大块，仍会形成局部串行区间；每phase判断“是否还有future”也产生控制成本。

**具体修改一：调整发射位置。** 每phase有16次A fragment LDS读取，将future B预取放在中间：

```text
较早安排：future B load → 16次A的DS读取 → 等待current B → MMAC
mixed安排：8次A的DS读取 → future B load → 8次A的DS读取
          → 等待current B → MMAC
```

这给global加载提前发射后留下后半DS工作的窗口；它只是发射次序，动态重叠仍取决于硬件与编译后的依赖。

**具体修改二：无条件future。** AQ把future load的终末判断移出热路径，包括最后一次无用预取；在边界受保护的前提下，末尾显式保留pending bank活跃、`vmcnt(0)`后再进入输出，避免在途load写坏被编译器复用的寄存器。

```cpp
// 原先每phase判断
if (next_phase < total_phases) issue_future();

// always候选的概念式
issue_future_with_audited_bounds();
...
wait_vmcnt(0);
keep_pending_bank_live_until_here();
write_output();
```

最终K32结构化实现还把terminal resource range设0，并在最后current消费前VM0；旧raw always路径与最终路径的终末策略需分别按源码看，不能混为同一种边界方案。

**实际结果。** AR独立mixed约246.38/246.40/228.56/246.51T；AT组合mixed+always约248.17/249.38/231.52/249.55T。AP的局部wave交错、AV的点4/12方案反而慢，最终保留经过验证的点8。`unroll2`曾与always产生同SHA，没有额外收益可计。

**xprof证据。** mixed/always各自没有独立配对counter；后续P02的AU包含这套主循环，还叠加了输出优化，只能描述AU整体。AV是由LDS等待方向引出的负结果，不能凭预取更早就推定更快。

**源码。** future条件与插入位置见[rolephase.cpp:727](<../rolephase.cpp:727>)、[rolephase.cpp:758](<../rolephase.cpp:758>)，终末drain见[rolephase.cpp:1028](<../rolephase.cpp:1028>)；宏 `H3_PHASE_MID_PREFETCH=1`、`H3_PHASE_MID_POINT=8`、`H3_PHASE_ALWAYS_PREFETCH=1`。阶段AP/AQ/AR/AS/AT，AR和AT各有独立72组/216次审计。

### 4.5 有界buffer写回与branchless BF16 RNE（AU/AY/AZ）

**原来的问题。** 输出循环对每个元素做token/feature判断与全局地址写入；浮点到BF16转换也有特殊数条件控制。在每个wave写出大量累加器时，这些控制和地址成本会重复出现。

**具体修改一：输出边界放进buffer resource。**

```cpp
// 修改前
if (feature < features && token < tokens)
    output[token * features + feature] = ck_bf16_rne(acc);

// 修改后，省略实际lane/fragment索引
res = make_buffer(output + token_tile_start * features,
                  remaining_token_rows * features * sizeof(BF16));
voffset = (local_token * features + feature_base) * sizeof(BF16);
buffer_store_short(ck_bf16_rne(acc), res, voffset,
                   soffset=0, immediate=fragment_feature_offset);
```

所有token偏移进入参与bounds check的voffset。soffset不参与该检查，因此不能把token位移挪入soffset以省指令；早期不安全版本被拦截，未作为可用结果。feature片段偏移由已验证N对齐约束保证合法。

**具体修改二：RNE改为整数选择。** 对FP32位模式u，有限数仍执行 `u + 0x7fff + ((u >> 16) & 1)`；指数全1的Inf/NaN走CK原有payload保留规则。`output_rne.hpp`用mask/select合并两路结果，减少逐输出的EXEC条件控制。

```cpp
rounded = u + 0x7fff + ((u >> 16) & 1);
special = u | (((u & 0xffff) != 0) << 16);
mask = 0u - unsigned((u & 0x7f800000) == 0x7f800000);
bf16_bits = ((rounded & ~mask) | (special & mask)) >> 16;
```

**实际结果。** AU达到255.54/258.33/243.97/258.37T；AZ的RNE独立复测为257.89/260.27/247.83/260.68T，相对同轮AU耗时下降约0.7%–1.6%。ISA中EXEC保存/恢复控制明显减少，MMAC、DS读和store_short静态数量不变。

**counter证据。** AK→AU工具报告SALU52.18M→29.61M、VALU258.28M→238.41M，LDS issue反而156.07M→173.70M。这对照还包含mixed/always等改动，不能把全部指令下降归于输出store。RNE本身的证据主要是位模式probe、ISA和配对计时，没有独立RNE xprof因果拆分。

**源码与验证。** [rolephase.cpp:1090](<../rolephase.cpp:1090>)输出循环，[output_rne.hpp:3](<../output_rne.hpp:3>)转换；宏 `H3_PHASE_BUFFER_EPILOGUE=1`、`H3_PHASE_OUTPUT_RNE=1`。RNE probe覆盖1,507,328个位模式，AU/AZ各有72组GEMM审计；不是穷举全部FP32或证明任意输入跨库bitwise一致。

### 4.6 重新安排producer/consumer同步，让下一A覆盖完整当前tile（BA/BB）

**原来的问题。** 较早协议初始装A0/A1，在当前tile的READY/ACK之后才发更远的下一A；权重加载、LDS释放和数学之间的等待安排限制了有效预取窗口。

**具体修改。** startup只装A0，compute同时准备B0；双方经两个匹配startup barrier完成各自VMEM。之后producer在当前tile一开始发下一tile的权重到另一LDS槽，让搬运覆盖两个K32数学phase。

```text
startup：producer发A0；consumer发B0；barrier → 各自VM0 → barrier

producer wave                         consumer wave（BA时的数学后同步形式）
发A(tile+1)到另一LDS槽                  读当前A phase0，完成phase0 MMAC
到达barrier 0       <----------------> 到达barrier 0
等待下一A的VMEM完成                    读当前A phase1，完成phase1 MMAC
到达barrier 1       <----------------> 到达barrier 1
开始下一tile；已释放旧槽可复用            开始下一tile
```

两槽的所有权明确：producer预取只写另一槽；当前槽必须等consumer已完成所需读取后才能被tile+2覆盖。最终BL的early/late两组把部分barrier相对数学位置改变，但仍遵循同一个“读取完成才释放”规则。

**为什么可能快。** 下一A的加载不必等到当前tile数学接近结束才开始；compute消耗两个phase时，producer可以同时推进权重搬运。每K64仍是两个匹配barrier，收益来自时序，不是把同步删掉。

**实际结果。** BB独立结果271.48/274.17/258.80/273.16T，较同轮旧RNE耗时下降5.01%/5.17%/4.23%/4.55%。VGPR221、LDS64KiB、无spill，与旧版本资源一致，不能解释为occupancy提高。

**counter证据。** 旧RNE→新cadence：LGKM131.35M→50.66M、barrier600.11M→460.05M；LDS issue173.17M→276.02M、VMEM issue14.99M→131.42M反而上升。说明同步节奏和发射竞争都变化，净收益以BB计时为准。

**源码与验证。** [rolephase.cpp:549](<../rolephase.cpp:549>) producer，consumer startup见[rolephase.cpp:703](<../rolephase.cpp:703>)，phase同步见[rolephase.cpp:997](<../rolephase.cpp:997>)。宏 `H3_PHASE_NATIVE_CADENCE=1`；BA/BB及72组/216次审计包含K64=1的启动和终末边界。

### 4.7 显式展开两个K64 tile，使LDS槽偏移编译期固定（BG/BH）

**原来的问题。** 单tile循环每轮根据运行时 `tile%2` 选择LDS槽；早期pragma unroll没有产生不同机器码，不能当作已经实现有效展开。

**具体修改。** 用always-inline lambda接收编译期slot_tag，每轮明确调用slot0/slot1：

```cpp

    consume(tile, slot=tile%2);

// 修改后
auto consume_pair_tile = [&](int tile, auto slot_tag) {
    constexpr int slot = decltype(slot_tag)::value;
    constexpr int lds_offset = slot * (FW * WK);
    // 两个K32 phase；保持原B bank、等待与barrier
```

奇数最后一个K64 tile只执行一次消费和对应producer握手，不能无条件执行第二个同步。B依然是K32双bank，没有扩成退化的K64激活双bank。

**实际结果。** BH约274.30/278.60/262.86/277.64T，相对同轮cadence耗时下降1.01%/1.61%/1.60%/1.64%。ISA静态MMAC128→256、DS读32→64，是两个tile的循环体展开，每次请求的动态乘加量没有增加。

### 4.8 静态wave分组，并把priority放到首条MMAC之后（BL/BM）

**原来的问题。** 动态stagger在每phase判断wave属于哪组：一组数学后barrier，另一组A读完后先barrier再数学。BF直接加入这种错位反而慢，单独在数学前提升priority也没有改善。

**具体修改。** 将整条K消费循环模板化，按编译期bool分别生成early/late两份body；每个wave在整个K循环前只选一次。然后把 `s_setprio 1` 放在每phase第一条MMAC之后，数学结束复位0。

```cpp
auto consume_wave_group = [&](auto tag) {
    constexpr bool early = decltype(tag)::value;
    for_each_K_tile_and_phase([&] {
        read_current_A_to_private_VGPR();
        wait_current_B();
        if constexpr (early) { wait_LGKM0(); barrier(); }
        MMAC_first();
        setprio(1);
        MMAC_remaining();
        setprio(0);
        if constexpr (!early) barrier();
    });
};
if (wave_id >= 4) consume_wave_group(number<1>{});
else              consume_wave_group(number<0>{});
```

early组只有在A已全部从LDS读进private VGPR后才允许producer复用共享槽；后续数学使用私有数据，不能先barrier后继续读取可能已被覆盖的LDS。两组的K累加顺序相同。

**为什么可能快。** wave组的分支和循环调度变成两套专门body，计算wave与producer的就绪/发射时机改变。priority位置也是组合的一部分，必须由组合对照证实，而不是从指令字面推断收益。

**实际结果。** BM约296.79/301.05/282.98/299.78T，较同轮双tile耗时下降7.50%/7.43%/7.07%/7.36%。仅静态分组约252–262T，数学前priority也慢；只有完整组合胜出。VGPR226→230，LDS不变，无spill，不是减少寄存器带来的收益。

**counter证据。** LDS issue286.79M→78.68M（下降72.6%）、barrier467.91M→333.81M；VM完成等待124.34M→200.99M上升。实际kernel时间只下降约7%，不能把72.6%当作性能收益。

**源码与验证。** [rolephase.cpp:672](<../rolephase.cpp:672>)静态body，[rolephase.cpp:836](<../rolephase.cpp:836>)early屏障，[rolephase.cpp:949](<../rolephase.cpp:949>)附近MMAC/priority，[rolephase.cpp:1042](<../rolephase.cpp:1042>)K循环外选择。宏 `H3_PHASE_STATIC_STAGGER=1`、`H3_PHASE_POSTPRIO=1`；BL/BM、102组/306次审计。

### 4.9 把B的公共K32位移放入标量resource指针（BO/BP）

**原来的问题。** 每个lane的raw B向量地址含相同K32起点，公共部分反复参与向量地址计算。即使数据量不变，地址指令及存活范围仍有成本。

**具体修改。** 把同一wave共有的K32起点移入resource pointer，resource byte bound等量减小，lane仅计算行号和片内坐标：

```cpp
// 修改前
voffset = (row * K + kk) * 2;
load_raw(resource(base, extent), voffset);

// 修改后，适用于已验证raw K32路径
common = readfirstlane((kk & ~31) * 2);
resource.pointer = base + common;
resource.byte_bound = extent - common;
voffset = (row * K + (kk & 31)) * 2;
load_raw(resource, voffset);
```

物理地址仍是 `base+2*(row*K+kk)`；bound与base一起移动，物理末端保持不变。末尾边界和更深K64预取的下溢条件不同，不能把上面的减法无保护用于K64候选。

**实际结果。** BP为298.73/307.74/285.51/306.52T，相对同轮静态分组耗时降低0.70%/2.26%/0.96%/2.23%。VGPR230→225、SGPR增加到31，说明向量/标量分配确实改变；资源变化本身不足以单独解释全部收益。

**xprof证据。** 有BP最终raw库四shape与rocBLAS的P06对照，没有BO前后两版的独立counter因果拆分。P06中out_proj VM等待/rocBLAS约5.92提示进一步查数据供给，不能把这个比值解释为B rebase收益。

**源码与验证。** [rolephase.cpp:400](<../rolephase.cpp:400>) `H3_PHASE_SCALAR_B_BASE` 分支；BO/BP及102组/306次广审计。历史raw基线库SHA以 `22ef3280...` 开头。最终结构化B采用下一节的descriptor方法，raw版本继续作为非目标尺寸fallback。

### 4.10 producer固定槽pair + 权重A的scalar offset，只给适合的投影用（CG–CK）

**原来的问题。** compute已经成对消费tile，但producer仍逐tile计算LDS槽；每条权重搬运的向量地址又包含相同tile K位移。单独调整producer并非所有shape都会获益。

**具体修改。** producer也每轮展开两个tile，显式 `stage_weight<1>` / `stage_weight<0>` 固定LDS槽；同时把权重公共 `tile*64*2` 字节位移放入硬件soffset，row/K片内偏移留voffset：

```cpp
// 较早权重搬运
voffset = (row*K + tile*64 + col) * 2;
load_direct_to_LDS(res, voffset, soffset=0, dynamic_slot);

// 新的有效权重tile搬运
common  = readfirstlane(tile*64*2);
voffset = (row*K + col) * 2;
load_direct_to_LDS(res, voffset, soffset=common, fixed_slot);
```

soffset不参与bounds，因此此helper仅用于已有完整feature tile、明确有效K tile的权重加载；producer仍以 `tile+1<count` / `tile+2<count` 保护发射。不能直接复用给M尾部激活或终末无用prefetch。

**实际结果。** CK两投影分派独立复测：FC2约300.17T、out约286.64T，相对原raw只降低约0.48%/0.38%时间；QKV/FC1保持原路径。收益小但两轮确认，未全局开启。

**xprof证据。** 没有这项producer组合单独配对counter，因此只报告实现、ISA/搬运probe、审计及独立计时。最终K32 Cache Swizzle分派继续只在FC2/out使用该组合，不能把最终全部增益归于它。

**源码与验证。** [rolephase.cpp:553](<../rolephase.cpp:553>)producer pair，[rolephase.cpp:355](<../rolephase.cpp:355>)搬运调用，[async_a_soffset.hpp:4](<../async_a_soffset.hpp:4>)硬件soffset，[shape_dispatch.cpp](<../shape_dispatch.cpp>)旧分派；宏 `H3_PHASE_PRODUCER_PAIRS=1`、`H3_PHASE_A_SOFFSET=1`。CG–CK，producer候选各102组、分派入口126组审计。

### 4.11 在快的K32流水中实现结构化Cache Swizzle，并按shape选组合（DD–DG）

**原来的问题。** 多轮早期cache候选使用不同操作数方向、等待位置或K64 bank，整个流水仍慢；“开启cache”本身不能修复这些问题。CZ的K64结构化ON虽然比同路径OFF快，但与raw相比只使out达到约292T。

**具体修改一：保留K32计算流水，只替换激活B加载的地址表达。** 为descriptor构造pow2 stride和逻辑行数，以 `idxen offen` 发结构化buffer读取。

```cpp
// 目标物理地址不变：base + row*(2*K) + 2*kk
S = largest_power_of_two_not_greater_than(2*K);
R = 2*K - S;
common = (kk & ~31) * 2;

res = structured_resource(base, stride=S, row_count=remaining_rows,
                          cache_swizzle=1);       // descriptor bit62
// 只移动低48位pointer，保留高位stride/cache属性
res.pointer_low48 = res.pointer_low48 + common;
if (common >= 2*K) res.row_count = 0;             // terminal无用读取

index   = row;
voffset = row*R + (kk & 31)*2;
data = buffer_load_dwordx4(res, index, voffset);  // idxen offen
```

地址等式为：`base + common + row*S + row*R + 2*(kk&31) = base + row*(2K) + 2*kk`。例如FC2 K7168：字节行跨度14336拆为S8192+R6144；QKV/FC1为10752=8192+2560；out为7168=4096+3072。

**具体修改二：同步和边界配套。** row count使用剩余逻辑token行数；terminal range为0；最后current bank消费前完整VM0，之后仍保留pending bank生命周期和末尾drain。更新pointer时若把高位stride/cache一并覆盖，或把row count当总字节数，可能地址正确性或边界失败。

**具体修改三：统一入口选择实测更快的组合。**

```cpp
if (N==5376 && (K==7168 || K==3584))
    return K32_cache_with_producer_pair_and_A_soffset(...); // FC2/out
if ((N==10752 || N==14336) && K==5376)
    return K32_cache_plain_producer(...);                  // QKV/FC1
return original_raw_K32(...);                              // 旧支持域回退
```

**实际结果：先看DD同轮OFF/ON，再看最终入口。** 下面按最终选择的producer配置配对，避免跨轮拼收益：

### 4.12 两个反例：减少资源或更早预取，为什么反而慢

**反例一：CS把feature tile256改128。** 同时将MT16→8、producer覆盖和槽大小配套减半；8compute+4producer不变，因此每lane累加器128→64，VGPR225→129、LDS64→32KiB，无spill。但是覆盖同一输出需要两倍CTA，数学/控制摊销变差，只175–181T。xprof显示waves×2、SALU×1.799、VMEM读×1.501；DTK VM等待×3.061、barrier×2.414。后续CT再把wave配成4+2只恢复到180–185T。

源码：[rolephase.cpp:240](<../rolephase.cpp:240>)及 `H3_PHASE_FEATURE_TILE` / `H3_PHASE_COMPUTE_WAVES` / `H3_PHASE_PRODUCER_WAVES` 分支；CPU覆盖检查[test_feature_tile.py](<../test_feature_tile.py>)；报告[FEATURE_TILE_EXPERIMENTS_20261013.md](<../FEATURE_TILE_EXPERIMENTS_20261013.md>)。

**反例二：CW在phase0 last-use后提前读phase1 A。** 每个或每4个A fragment最后一次phase0 MMAC完成后，立即复用av去读phase1，phase1跳过原始加载并保留LGKM完成保护。ISA中DS与MMAC静态交错0→64，说明优化真实进入机器码，但VGPR225→241，吞吐降到274–281T。stream4的VM等待×1.150、barrier×1.155、LDS issue×1.254，虽然LGKM降到0.531倍，总体仍慢。

源码：[rolephase.cpp:770](<../rolephase.cpp:770>)预取窗口/跳过原读取，及 `H3_PHASE_A_PHASE1_PREFETCH` 的MMAC last-use发射分支；报告[A_PHASE1_STREAM_EXPERIMENTS_20261013.md](<../A_PHASE1_STREAM_EXPERIMENTS_20261013.md>)。这些结果解释了为何后续迭代必须同时核对寄存器寿命、等待与实际计时，不能只看源码里是否“多重叠了一步”。

### 指标的使用边界

- 等待值为跨wave/per-SIMD聚合，本机catalog以4cycles为单位，且nondeterministic。不能相加为kernel总时间，不能直接换算E2E占比。
- xprof和rocprof是不同采集运行；同列均值不构成一条可还原的联合时间线。性能排名只用无profiler的HIP event。
- 本机SQ指令、LDS bank-conflict部分是emulated；0 bank conflict不是证明物理零冲突。
- 本机xprof FetchSize只覆盖EA0，而DTK gfx936表达式含EA1；不能把它未经校正当完整HBM流量或roofline依据。full replay也会扰动UTCL2。
- `.perf`与SQTT raw已留存，但尚未用兼容XCompute解析成逐指令时间轴；文档不编造精确源行stall latency或occupancy。
- 最终DTK初次过滤未包含命名空间新kernel，只得到旧版+库6项；补入h3_struct32后重采得到9项。原文件保留，缺失从未当0，正式计时未重跑。
